Unit 01

DBMS Architecture

The foundation. Understand how DBMS is structured and why it's better than file systems.

⭐

Most Important for Exam: Three-level architecture, data independence (physical vs logical), DDL vs DML — these appear in nearly every university exam.

A Database Management System (DBMS) is software that manages, stores, retrieves, and manipulates data in a structured way. Think of it as a highly intelligent librarian who not only stores books but can find any information instantly, ensure no two people check out the same book simultaneously, and recover from disasters.

File System vs DBMS — The Classic Comparison

ParameterFile SystemDBMS
Data RedundancyHigh — same data repeatedLow — controlled via normalization
Data InconsistencyVery commonEliminated
Data SharingDifficultEasy concurrent access
SecurityOS-level onlyFine-grained access control
Backup & RecoveryManualAutomatic with logs
Data IndependenceNone — app depends on file structurePhysical & Logical independence
Query LanguageNoneSQL
💡 Memory Trick

DBMS Advantages = R-I-S-Q-D-A → Redundancy↓, Inconsistency↓, Sharing↑, Query Language, Data Independence, Access Control

The three-schema architecture separates the user's view from the physical storage, enabling data independence.

👁
External Level (View)
What individual users see. Each user has their own customized view. E.g., HR sees employee data, Finance sees salary data only.
🧩
Conceptual Level (Logical)
Community view — describes what data is stored and relationships. Hides physical storage details. DBA works at this level.
💿
Internal Level (Physical)
Actual physical storage — how data is stored on disk, file organization, indexes, compression. Closest to hardware.

Data Independence — The Big Idea

Physical Data Independence: Ability to change the physical schema without affecting the conceptual schema. Example: changing file organization from sequential to hash without rewriting applications.

Logical Data Independence: Ability to change the conceptual schema without affecting external schemas. Example: adding a new column to a table without breaking existing views. Harder to achieve than physical independence.

📝 Exam Trick

Physical independence is EASIER to achieve. Logical independence is HARDER. If asked which is more important — both are, but logical is more difficult to achieve.

Also remember: DCL (GRANT, REVOKE), TCL (COMMIT, ROLLBACK, SAVEPOINT)

Schema vs Instance

Schema = The overall design/structure of the database (like a blueprint). Rarely changes.

Instance = The actual data stored at a particular moment (like the actual building). Changes constantly.

🎯 Analogy

Schema is like a class definition in OOP. Instance is like an object created from that class.

Integrity Constraints

Domain constraint: Values must be from a defined domain (age must be integer > 0).

Entity integrity: Primary key cannot be NULL.

Referential integrity: Foreign key must reference an existing primary key or be NULL.

Key constraint: Each tuple must be uniquely identified.

💡 Exam Trick

Entity integrity → PK cannot be NULL. Referential integrity → FK must exist in referenced table. These two are the most asked.

Unit 03

Relational Query Languages

The mathematical foundation of SQL — master these operators to ace MCQs and theory questions.

⭐

Most Important: Relational Algebra operators, especially SELECT (σ), PROJECT (π), JOIN, and DIVISION are extremely high frequency in exams.

σ
Select
Filters rows based on a condition. Like WHERE clause. σcondition(R)
π
Project
Selects specific columns. Eliminates duplicates. Like SELECT col. πcol1,col2(R)
∪
Union
Combines tuples from two relations (no duplicates). Relations must be union-compatible.
−
Difference
Tuples in R but not in S. R − S
×
Cartesian Product
All possible combinations of tuples. R × S. Result: |R|×|S| tuples.
ρ
Rename
Renames a relation or attributes. ρnewName(R)
⋈
Natural Join
Joins on common attributes, removes duplicate columns. Most common join type.
⋈θ
Theta Join
Join with any condition (=, >, <). General case of join.
⋈=
Equi Join
Theta join where condition is only equality (=). Keeps both join columns.
÷
Division
Finds tuples in R that are related to ALL tuples in S. "For all" queries.
∩
Intersection
Common tuples in R and S. Not fundamental (derived from − and ∪).

Example — Step by Step

Given: EMPLOYEE(EID, NAME, DEPT, SALARY) — Find names of CS employees earning > 50000:

πNAME( σDEPT='CS' AND SALARY>50000( EMPLOYEE ) )
📝 Order Rule

Always apply σ (SELECT) before π (PROJECT) for efficiency. Apply most restrictive condition first. This is the basis of query optimization.

Tuple Relational Calculus (TRC)

Non-procedural language — specifies WHAT to retrieve, not HOW. Uses tuple variables: {t | P(t)} where t is a tuple variable and P is a predicate.

Example: Find students with GPA > 3.5: {t | t ∈ STUDENT ∧ t.GPA > 3.5}

Domain Relational Calculus (DRC)

Uses domain variables (one per attribute). {⟨x1,x2,...⟩ | P(x1,x2,...)}

QBE (Query By Example)

Graphical query language. User fills in example values in table skeleton. Internally converts to relational algebra. Found in Microsoft Access.

Unit 04

Relational Database Design & Normalization

The most exam-heavy topic. Master functional dependencies and normal forms.

🔥

Guaranteed in Exam: Every university exam has normalization numericals. You MUST be able to identify 1NF, 2NF, 3NF, BCNF and decompose schemas.

A Functional Dependency (FD) X → Y means: knowing X uniquely determines Y. If two tuples have the same X value, they must have the same Y value.

Types of Dependencies

Full Dependency
Y depends on the entire composite key, not just part of it. Required for 2NF.
Partial Dependency
Y depends on only PART of a composite key. Violates 2NF. Only possible with composite key.
Transitive Dependency
X→Y→Z (Y is non-key). Z transitively depends on X. Violates 3NF.
Trivial Dependency
A→B where B ⊆ A. Always holds. Not interesting for normalization.

Armstrong's Axioms

AxiomRuleMeaning
ReflexivityIf Y ⊆ X, then X → YA set of attributes determines its own subsets
AugmentationIf X → Y, then XZ → YZAdding same attribute to both sides preserves FD
TransitivityIf X→Y and Y→Z, then X→ZChaining of FDs

Derived rules: Union (if X→Y and X→Z, then X→YZ), Decomposition, Pseudo-transitivity

💡 Memory Trick: Armstrong = RAT

Reflexivity, Augmentation, Transitivity — Armstrong's three primary axioms are like a RAT that gnaws through all FDs!

Closure of Attribute Set (X+)

The closure X+ is the set of ALL attributes that can be determined from X using the given FDs.

Algorithm: Start with result = X. For each FD A→B, if A ⊆ result, add B to result. Repeat until no change.

Use: If X+ = all attributes → X is a superkey. If no proper subset of X has this property → X is a candidate key.

1NF
First Normal Form
A relation is in 1NF if: (1) All attribute values are atomic (no multi-valued or composite attributes), (2) There are no repeating groups, (3) Each row is unique (has a primary key).
Violation: Multi-valued cell like {Math, Science} in one cell
2NF
Second Normal Form
In 1NF + No partial dependencies. Every non-key attribute must depend on the ENTIRE composite primary key. Only relevant when PK is composite.
Violation: (StudentID, CourseID) → StudentName (StudentName depends only on StudentID)
3NF
Third Normal Form
In 2NF + No transitive dependencies. No non-key attribute should depend on another non-key attribute. For any FD X→Y: either X is a superkey OR Y is a prime attribute (part of some candidate key).
Violation: EmpID→DeptID→DeptName (DeptName transitively depends on EmpID via DeptID)
BCNF
Boyce-Codd Normal Form
Stronger than 3NF. For every FD X→Y, X must be a superkey. A relation in BCNF is also in 3NF, but not vice versa.
BCNF may not always preserve dependencies — trade-off with 3NF

Quick Identification Cheat Sheet

Normal FormViolation To RemoveKey Requirement
1NFAtomic values onlyNo multi-valued attributes
2NFPartial dependenciesFull dependency on PK
3NFTransitive dependenciesNo non-key→non-key
BCNFLHS must be superkey for ALL FDsStronger than 3NF

Lossless Decomposition

A decomposition R into R1 and R2 is lossless if: R1 ∩ R2 → R1 or R1 ∩ R2 → R2 (the common attribute is a key in at least one of the relations).

Dependency Preservation

All functional dependencies from the original relation should still be enforced after decomposition (either directly or derivable). BCNF may not always preserve dependencies — use 3NF when dependency preservation is required.

📝 Normalization Shortcut

Step 1: Find all candidate keys. Step 2: Check each FD. Step 3: Classify violation. Step 4: Decompose. The common mistake is forgetting to recheck after decomposition.

SQL Masterclass

SQL — Complete Reference

The most practical and exam-scoring section. Master every command, clause, and pattern.

🔥

Guaranteed 20–30 marks: SQL questions appear in every exam. Know CREATE TABLE, SELECT with JOINs, aggregate functions, subqueries, and views cold.

SQL — DDL
-- CREATE TABLE with all constraints CREATE TABLE Student ( StudentID INT PRIMARY KEY, Name VARCHAR(50) NOT NULL, Email VARCHAR(100) UNIQUE, Age INT CHECK (Age > 0 AND Age < 120), Gender CHAR(1) DEFAULT 'M', DeptID INT REFERENCES Department(DeptID) ); -- ALTER: Add, Modify, Drop columns ALTER TABLE Student ADD Phone VARCHAR(15); ALTER TABLE Student MODIFY Name VARCHAR(100); ALTER TABLE Student DROP COLUMN Phone; -- DROP vs TRUNCATE vs DELETE DROP TABLE Student; -- Removes table + structure TRUNCATE TABLE Student; -- Removes all data, keeps structure DELETE FROM Student; -- Removes data, can be rolled back
📝 DROP vs TRUNCATE vs DELETE

DROP = Removes table entirely (DDL, no rollback). TRUNCATE = Removes all rows fast (DDL, no rollback, resets identity). DELETE = Removes rows conditionally (DML, can rollback). This is very commonly asked!

Limit output -- Aggregate functions SELECT COUNT(*), SUM(Salary), AVG(Salary), MIN(Salary), MAX(Salary) FROM Employee WHERE Dept = 'CS' GROUP BY DeptID HAVING AVG(Salary) > 50000;

📝 WHERE vs HAVING

WHERE filters individual rows BEFORE grouping. HAVING filters groups AFTER GROUP BY. You CANNOT use aggregate functions in WHERE. WHERE AVG(sal) > 5000 = WRONG. HAVING AVG(sal) > 5000 = CORRECT.

SQL — JOINs
-- INNER JOIN: only matching records SELECT s.Name, c.CourseName FROM Student s INNER JOIN Enrollment e ON s.StudentID = e.StudentID INNER JOIN Course c ON e.CourseID = c.CourseID; -- LEFT JOIN: all students, even without enrollment SELECT s.Name, e.CourseID FROM Student s LEFT JOIN Enrollment e ON s.StudentID = e.StudentID; -- SELF JOIN: find employee and their manager SELECT e.Name AS Employee, m.Name AS Manager FROM Employee e JOIN Employee m ON e.ManagerID = m.EmpID;
SQL — Advanced
-- Subquery: students with above-average salary SELECT Name FROM Employee WHERE Salary > (SELECT AVG(Salary) FROM Employee); -- Correlated subquery SELECT e1.Name FROM Employee e1 WHERE Salary > (SELECT AVG(Salary) FROM Employee e2 WHERE e2.DeptID = e1.DeptID); -- EXISTS: students enrolled in at least one course SELECT Name FROM Student s WHERE EXISTS (SELECT 1 FROM Enrollment e WHERE e.StudentID = s.StudentID); -- VIEW: virtual table CREATE VIEW CS_Students AS SELECT * FROM Student WHERE DeptID = 1; -- INDEX: speed up queries CREATE INDEX idx_name ON Student(Name); CREATE UNIQUE INDEX idx_email ON Student(Email);
💡 View vs Table

A VIEW is a stored query — it doesn't store data itself, just the SELECT statement. Views provide security (show only specific columns/rows) and simplify complex queries.

Unit 05

Query Processing & Optimization

How DBMS translates and optimizes SQL queries for maximum performance.

1. Parsing & Translation
SQL query is parsed for syntax errors, then translated into an equivalent relational algebra expression. Ambiguous names are resolved using the schema catalog.
2. Query Optimization
The optimizer generates multiple equivalent query execution plans and estimates their cost using statistics (cardinality, selectivity). Picks the cheapest plan.
3. Query Evaluation
The chosen execution plan is executed by the query execution engine. Results are returned to the user.

Heuristic Optimization Rules

  • Push σ (select) down: Apply selections as early as possible to reduce tuple count
  • Push π (project) down: Keep only needed columns early to reduce tuple size
  • Perform most restrictive σ first: Apply the condition that eliminates most tuples first
  • Combine cascaded σ: Multiple selects on same relation → combine into one
  • Reorder joins: Use smaller intermediate results to reduce computation

Join Algorithms

AlgorithmBest ForComplexity
Nested Loop JoinSmall relations, any join conditionO(n × m) — expensive
Sort-Merge JoinBoth relations sorted on join attributeO(n log n + m log m)
Hash JoinEqui-joins, large unsorted relationsO(n + m) average
Index JoinOne relation has index on join attributeO(n × log m)

Storage Strategies

Indexes, B-trees, and hashing — the mechanisms that make databases fast.

Index TypeDescriptionWhen to Use
Primary IndexBuilt on ordered key field. One entry per block (sparse). Data file is ordered on this key.On primary key of ordered file
Secondary IndexBuilt on non-ordering field. Dense — one entry per record.For fields queried often but not the ordering key
Clustering (Clustered)Data rows stored in same order as index. Only ONE per table possible.Range queries, ORDER BY on same column
Non-ClusteringIndex order differs from data order. Multiple per table.Point queries on non-primary keys

💡 Memory Trick

Dense = entry for every record (like everyone has their own locker key). Sparse = entry for every block (like one master key per floor). Dense takes more space but faster for point queries.

B+ Tree (Most Important Data Structure)

B+ trees are the most commonly used index structure. All data pointers are in leaf nodes only. Internal nodes store only keys for routing. Leaf nodes are linked in a doubly-linked list for efficient range queries.

Properties: Every node has between ⌈n/2⌉ and n children (n = order). Root has at least 2 children. All leaves at same level (balanced).

FeatureB-TreeB+ Tree
Data pointersAt all nodesOnly at leaf nodes
Leaf linkingNoYes — linked list
Range queriesSlowerFaster (leaf scan)
Key duplicationNo — key appears onceYes — key may repeat at internal nodes

Hashing

A hash function h(K) maps key K to a bucket number. Static hashing: Fixed number of buckets. Dynamic hashing (extendible/linear): Buckets grow as needed.

Collision handling: Open addressing (linear probing, quadratic probing), Chaining (overflow buckets).

Unit 07

Transaction Processing

ACID, concurrency control, locking, deadlocks — the heart of reliable database systems.

🔥

Very Important: ACID properties, serializability, 2PL, and deadlock handling appear in every exam. The ACID mnemonic alone can get you 5+ marks.

ACID Mnemonic
A
Atomicity
C
Consistency
I
Isolation
D
Durability
"All Committed In Database" — helps remember all four properties
⚛️
Atomicity
All or Nothing. A transaction either fully completes or fully fails. If it fails midway, all changes are rolled back. Ensured by UNDO logs / shadow paging.
✅
Consistency
Valid state to valid state. A transaction takes the database from one consistent state to another. All integrity constraints must hold before and after.
🔒
Isolation
Concurrent transactions don't interfere. Intermediate states of a transaction are invisible to other transactions. Ensured by locking / MVCC / timestamp ordering.
💾
Durability
Committed changes survive failures. Once committed, changes persist even after system crashes. Ensured by REDO logs, checkpointing.

Transaction States

Active
Transaction is executing its read/write operations. Initial state.
Partially Committed
Final operation executed, but changes not yet written to disk.
Committed
All operations successfully completed and changes durably written. COMMIT issued.
Failed
Normal execution cannot proceed (error or abort detected).
Aborted
Transaction rolled back to initial state. ROLLBACK executed.

Problems Without Concurrency Control

ProblemDescriptionExample
Dirty ReadReading uncommitted data of another transactionT2 reads T1's write before T1 commits
Lost UpdateTwo transactions overwrite each other's updatesBank debit race condition
Non-repeatable ReadSame query returns different values within same transactionValue changes between two SELECTs
Phantom ReadNew rows appear/disappear between readsCOUNT changes between two SELECTs

Lock Types

Shared Lock (S / Read Lock): Multiple transactions can hold simultaneously. Used for reading. Notation: lock-S(X)

Exclusive Lock (X / Write Lock): Only one transaction can hold. No other lock allowed. Used for writing. Notation: lock-X(X)

Two-Phase Locking (2PL)

Protocol ensuring serializability. Two phases:

Growing phase: Acquire locks. Cannot release any lock.

Shrinking phase: Release locks. Cannot acquire any new lock.

The point of transition is called the lock point. Transactions are serializable in order of their lock points.

Strict 2PL: Hold all exclusive locks until COMMIT. Prevents cascading rollbacks.

💡 2PL Rule

2PL guarantees conflict serializability BUT can cause deadlocks. Strict 2PL additionally prevents cascading rollback. This distinction is frequently asked.

Deadlock Handling

Prevention: Wound-Wait (older wounds/kills younger) or Wait-Die (older waits, younger aborts).

Detection: Maintain wait-for graph. Deadlock exists if there's a cycle in the graph.

Recovery: Select victim, rollback one or more transactions to break the cycle.

Timestamp-Based Concurrency Control

Each transaction gets a unique timestamp TS(T). For each data item X: TS-read(X) and TS-write(X) track the latest successful read/write timestamps. Thomas' Write Rule: if TS(T) < TS-write(X), ignore the write (outdated write).

MVCC (Multi-Version Concurrency Control)

Maintains multiple versions of data items. Readers don't block writers; writers don't block readers. Each transaction sees a consistent snapshot. Used in PostgreSQL, Oracle, MySQL InnoDB.

Log-based Recovery: Every operation is recorded in a log file (UNDO log / REDO log) before being applied to the database.

UNDO (Deferred Update): Don't write changes to DB until commit. On failure, just discard. UNDO log stores old values.

REDO (Immediate Update): Write changes immediately. On failure, redo committed transactions. REDO log stores new values.

Checkpointing: Periodically write all modified buffers to disk and record a checkpoint in the log. On recovery, only process transactions after the last checkpoint — reduces recovery time significantly.

Shadow Paging: Maintain a shadow copy of the database pages. Current pages are modified; shadow is untouched. On commit, shadow becomes the new current. On failure, current is discarded and shadow restored. Eliminates need for undo log but expensive for large DBs.

📝 Recovery Quick Summary

UNDO = revert uncommitted. REDO = replay committed. Checkpoint = reduce recovery scope. Shadow paging = simple but costly. Most real systems use ARIES (UNDO + REDO + checkpointing combined).

ODBC — Open Database Connectivity

ODBC is a standard API for accessing DBMSs from programming languages. Provides a common interface regardless of the DBMS. Applications connect via ODBC driver → ODBC Driver Manager → Database.

Database Administration Basics

GRANT/REVOKE: GRANT SELECT ON Student TO alice; — Give alice permission to read Student table. REVOKE SELECT ON Student FROM alice; — Remove permission.

Popular RDBMS comparison: Oracle (enterprise), MySQL (web), PostgreSQL (advanced open-source), DB2 (IBM enterprise), SQL Server (Microsoft), INFORMIX (OLTP), SYBASE (analytics).

Exam Day

Exam Strategy

Maximize your score even with limited preparation time.

01
🎯 Most Scoring Topics
Focus on: SQL (20-30%), Normalization (15-20%), ACID/Transactions (15%), ER Diagrams (10%), Relational Algebra (10%). These 5 areas cover 70%+ of marks in most universities.
02
⚡ 1-Day Revision Plan
Morning: ACID + Transactions (2hr). Afternoon: Normalization + FDs (2hr). Evening: SQL + Joins (2hr). Night: Relational Algebra + Quick Revision cards (1hr). Don't try to learn new topics — reinforce what you know.
03
📝 Theory Answer Strategy
Structure: Definition (2 lines) → Properties/Types (bullets) → Example → Diagram if applicable → Comparison table. Always include a diagram — even a rough one adds 2-3 marks.
04
💻 Solving Normalization
Step 1: Find all candidate keys (compute closures). Step 2: Check each FD against the normal form rules. Step 3: Identify violation type. Step 4: Decompose. Step 5: Verify lossless (R1∩R2→R1 or R2).
05
❓ MCQ Elimination
For MCQs: Eliminate obviously wrong answers first (usually 2 can be eliminated quickly). Between remaining 2 — look for absolute keywords: "always", "never", "all", "none" — these are often traps. Pick the most precise definition.
06
🕐 3-Hour Exam Plan
Hour 1: Attempt all MCQs + short questions you know well. Hour 2: Long questions — SQL queries + normalization numericals (most marks). Hour 3: Remaining theory + review answers. Never leave an MCQ blank.
